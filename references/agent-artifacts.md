# Agent 过程资料：深挖、去向与恢复

## 必须交付的判断

对占用大的项目，按子任务、生成器和文件类型拆分。记录逻辑大小、实际分配空间、创建/修改时间分布、最后写入进程、任务回执、输入与输出位置、下一次续跑的消费者。年龄和父项目状态只是线索。目录叫 tmp、fixture、archive、output 都不能单独决定去留。

先按大小分组，再对候选做完整 SHA-256；同 inode、硬链接、APFS 克隆和稀疏文件单独说明。重复字节总量只表示调查机会，不等于实际可释放空间。引用检查须覆盖具体路径、目录拼接、glob、manifest、构建脚本和续跑说明；basename 命中须判断究竟指向正式数据还是临时副本。

任务证据优先级：仍运行或仍被读取 → 保留；正式交付提交已合入且该旧步骤不会再消费 → 可以继续核验；仅测试 pass、最后一轮 completed、会话归档或长期无修改 → 结束状态未知。具体子任务可已结束而父项目仍进行中，不能因此改整个项目台账。

## 存储去向

| 对象 | 合理位置与删除前提 |
|---|---|
| 网站运行所需代码、配置、当期构建 | 按既有发布流程部署 VPS；核对磁盘容量和版本保留策略，不把 VPS 当通用归档盘 |
| 已公开的视频、音频、图片与下载包 | 既有公开对象存储/CDN；核对对象键、版本、长度和完整哈希，线上 URL 存在只证明发布对象存在 |
| 原镜头、音轨、角色参考、模型输出、工程与未公开成果 | 本地工作集及私有备份；不能上传公开桶充当备份，不能从最终 MP4 反推已保存全部源文件 |
| Git 已保存的正式源文件 | 保留可达提交与远端同步证据；Git LFS 指针不代表大文件已备份 |
| 已结束任务的完整复制件、旧索引 | 保留可恢复来源和回执后逐项清理，不删真实 Git 管理目录 |
| 构建与计算的暂存 | 明确重建输入、工具、参数、费用和续跑依赖；有确定重建途径且不再使用才清理 |

为每组给出“现在占多少、建议留哪里、已验证什么、缺什么、这次怎么处理”。不要把一百 GB 的原素材保留结论缩成“其他文件都留着”。缺少云端验证时，继续调查现有备份配置、范围、排除规则和回执，不要求用户自行复制一大串资料。

备份核验至少包含：最近成功时间、失败项目、排除范围、逐文件映射与可读回恢复。相同路径和相同大小不是相同内容；备份脚本若这样跳过工作树副本，应标为覆盖缺口。对象列表/ETag/上传成功日志不自动等于完整 SHA-256。删除本地唯一副本前验证实际恢复；远端只覆盖一部分就只对那部分计量。先查已有授权，新增存储目的地、费用或公开范围须单独明确。

## Git 复制件证明

单个 `method: delete, scope: all` 条目的 `checkpoint`：

```json
{
  "kind": "git_blob_copy",
  "owner_repo": "/absolute/project",
  "repo": "/absolute/retained-repository",
  "commit": "完整40位提交号",
  "retain_ref": "refs/remotes/origin/main",
  "git_path": "relative/path/data.json",
  "sha256": "完整SHA256",
  "task": {
    "root": "/absolute/project/scratch/finished-task",
    "role": "test_copy",
    "repo": "/absolute/project",
    "commit": "已合入的完整40位交付提交号",
    "retain_ref": "refs/remotes/origin/main",
    "receipt": "/absolute/project/scratch/finished-task/delivery.json",
    "receipt_sha256": "回执SHA256",
    "commit_pointer": ["candidate"]
  }
}
```

`role` 只允许 `test_copy` 或 `release_candidate`。校验文件实际所属仓库、ignored 且未跟踪、无软硬链接、精确 blob 相同、cat-file 恢复完整哈希相同；任务回执字段必须绑定已合入保留引用的交付提交。恢复仓库与回执不能同时列入清理目标。check、seal、act 均保留原有活动、引用与保护检查；保护项目不例外。计划与 seal 是逐文件恢复清单，必须保留。

恢复时先确认目标不存在，再从记录的 `repo + commit + git_path` 导出到新文件，核对记录的 SHA-256 后交付；不要覆盖后来重建的文件。远端同步状态另行核实：本机 `origin/main` 是本机引用，不能单独证明网络端仍持有对象。

必须拒绝的反例：空证明、仅 blob 存在但提交不可达、任务尚未合入、回执被改、正式跟踪文件、嵌套仓库归属不符、LFS 内容只有指针、恢复来源也被删除、父项目受保护。

## 精简视频验收页

适用于旧本地 HTML 把现存 MP4 再次 base64 内嵌的情况。脚本只处理已识别的播放器格式；其他格式保留，不能正则批量删 script。先通过 `peek.py` 的授权范围，再运行：

```sh
python3 scripts/compact_review.py plan --root <具体验收目录> --run <run目录> --out <run目录>/compact-plan.json
python3 scripts/compact_review.py apply --plan <清单> --seal <打印的摘要> --reason '<本轮授权>' --pilot
python3 scripts/compact_review.py apply --plan <清单> --seal <同一摘要> --reason '<本轮授权>'
```

脚本要求每段视频与同目录树内 MP4 完整哈希一致，页面未跟踪、24 小时无变化、未被打开，保留权限/扩展属性/ACL，并先模拟逐字节恢复原 HTML。清单保存网页文本壳和媒体哈希，不额外保存一份巨型网页。保留清单及其中列出的 MP4；页面改为相对引用，单独发网页文件将不能播放。试点后验证播放器路径、视频可读性与反馈文字；浏览器不可用时如实说明未完成视觉验收，不能声称看过页面。

需要重新生成原始单文件网页时：

```sh
python3 scripts/compact_review.py apply --plan <清单> --seal <摘要> --reason '<恢复依据>' --restore
```

恢复会核对当前精简页和保留视频，后续改过的页面拒绝覆盖。试点后的正式执行会跳过已经精简的试点页，统计须合并两份回执并按路径去重，不能重复计算。

## 更快的下一轮与源头治理

复用扫描清单、已识别生成器和来源映射；指纹变化、引用范围变化或新失败才重查对应项。删除前的实时活动、身份、恢复和保护检查不能复用旧绿灯。大目录要有覆盖率与未判断体积，不能为了快只清小缓存。

生产器应记录输入/输出、任务状态、交付提交、公开对象与私有备份映射；结束后保留最小回执和必要源文件，回收已证实冗余副本。验收页默认引用媒体，避免每次迭代嵌入一整份视频。归档采用完整内容哈希与恢复检查，避免按大小跳过同名不同内容。修改他人正在维护的生产器前先核对现场；“已提出治理方案”与“已实施并验证”分别报告。

独立模型复核只发送本轮授权范围内的脱敏证据，保留实际模型名、请求回执与完整结束状态。先保存本机初判，再比较双方同意、分歧及最终本机验证结果；模型没有直接访问磁盘时必须说明。调用失败或空响应不计为完成复核，也不自行更换用户指定模型后隐瞒。
