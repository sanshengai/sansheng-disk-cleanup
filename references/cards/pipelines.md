# 自建 AI 流水线（批量生成、渲染、构建发布）

适用于用户自己写脚本跑的批量任务：批量生图、视频渲染、转写、数据加工、站点构建与发布。这类目录没有通用路径，要靠证据判断。

## 存储位置

路径因人而异，下表是常见形态，扫描时按"谁写的"归类。

| 路径形态 | 内容 | 性质 |
|---|---|---|
| Agent 的生成图目录（如 `~/.codex/generated_images/<会话 id>/`） | 工具生成的原图，常被脚本再复制到成品目录 | 默认用户独有成果；生成接口通常不能逐字节复现，需核实另一份完整副本 |
| 流水线的 `out/`、`runs/`、`outputs/`、`.cache/` | 批量任务输出与回执 | 常是续跑依赖，见下文 |
| 战役树里的 `.local/`、`tmp/`、`work/` | 实验、转写缓存、渲染中间稿 | 先当用户独有成果，通过证据降级 |
| 成品目录（视频成片、图集、导出包） | 最终交付物 | 用户独有成果 |
| 构建暂存（如 `~/.<项目>/build-tmp`）、发布快照目录 | 每次构建或发布留下的整站副本 | 可再生缓存，但会反复增长，要改保留规则 |
| 渲染工程、镜头中间稿（被 git 忽略） | 成片的上游素材 | 默认独有上游素材；成片上线不能证明原镜头、音轨、工程已备份 |

## 怎么判断还在用

只有正向证据能支持删除。逐项对账，不凭印象。

- 回执/manifest/accepted 清单：脚本是否写了"某目录已复制到成品"的回执；回执条目数是否与目录数一致。只对账成功的部分计入可删体积，对不上的部分保留。
- 上线与确认记录：成品是否已提交、部署，是否有交接或确认文字；以提交与线上状态为准，不以"文件在"为准。
- 数量对得上：成片目录里的文件数、清单里的条目数、中间稿的条目数三者比对。差额部分当作未交付。
- 续跑依赖：被受跟踪脚本当输入读取的目录；断点续跑说明提到的 `out/`、缓存目录；脚本里写死的路径。搜索方法：对候选路径及其 basename 在受跟踪文件里 `git grep -F`（扫描器的 `refs` 字段已做）。
- 24 小时内有改动，或 `lsof` 显示被打开：视为进行中。
- 发布快照、构建暂存：判断的不是"这份能不能删"，而是"保留规则是什么"。先找生成它的脚本，看有没有回收逻辑、租期、数量上限。
- 增长对比：与上次扫描比较，每天/每次发布都涨的目录属于治理对象。

对账小抄（把"感觉可删"变成"证据可删"）：

```
git grep -F -l "<目录 basename 或绝对路径>"        # 受跟踪文件引用
grep -rF "<路径>" <交接记录或清单目录>             # 文字记录引用
ls <回执目录> | wc -l ; ls <目标目录> | wc -l     # 回执数量与目录数量对账
git log --oneline -n 5 -- <成品路径>               # 成品是否已提交
```

写进计划的 evidence 至少有三类里的两类：回执对账、上线或提交记录、引用检查结果。只有一类就降为 decide 并向用户提问。

## 原生清理与保留设置

- 优先改源头：给发布器、构建脚本加保留规则（按时间租期或份数上限），而不是每次手删。示例规则：保留最近 N 份或最近 48 小时，且当前线上引用的那份永不回收。
- 脚本自带的清理参数、`--keep`、`gc` 子命令优先于手删。
- 工具的保留设置见各 Agent 知识卡（会话保留天数、worktree gc 等）。
- 批量生成图：确认成品里引用了哪些，把被引用的逐个排除（写进 keep 列表），其余再按回执对账后删除。
- 每条删除建议在封存前走引用检查，把结果写进 `evidence`。

## 不能做的事

以下是三个匿名化的实战反例，每一个都在初判时被认为"可清理"，核验后被推翻：

- 反例一，"无引用"的生成图：分析工具说整个全仓搜不到引用，但交接记录里写明"保留"；记录称已另存副本，而副本目录早已删除，网盘清单只对上约 2%。教训：搜不到引用要同时查文字交接记录；"有副本"必须核实副本真实存在。
- 反例二，"很久没动"的实验目录：几个战役树里的 `.local` 目录超过一个月没有修改，但受跟踪的预处理脚本和续跑说明直接读取它们，里面有时长近 20 小时音频的转写缓存。教训：无改动 ≠ 无依赖；续跑依赖要查脚本读取路径。
- 反例三，"没有会话文件"的图目录：估算可删 4.98GB，按回执逐个对账只能证明 2.57GB 已复制成品。教训：没有会话文件只说明没有来源记录，不说明成品已落地；只删有回执的部分。

通用结论：

- "多久没动""没有会话文件""可以重新生成"三者不能单独作为删除理由；它们只是辅助信号。
- 引用检查必须在每条建议前做：受跟踪文件、清单、交接记录里是否出现该路径。
- 不要对发布快照、构建暂存反复手删；这说明保留规则缺失，应该改规则。
- 估算体积与按回执计量的体积要分开写，不要把估算当成效果承诺。

## 给用户的一句话问题

"<目录> 里有 N 个子目录对得上回执、已经在成品里；另外 M 个对不上，可能是中间稿也可能是没交付的内容。前者我清掉，后者你说留还是删？"

## 深挖与防止重复增长

按 [agent-artifacts.md](../agent-artifacts.md) 核对具体任务、存储去向和恢复证据。验收页优先相对引用现存媒体，不把同一个 MP4 再 base64 嵌入每版网页。测试副本与发布候选记录来源提交、任务完成回执和保留期限；结束时逐文件核对，不对整个进行中项目执行通配删除。改生产器属于另一个具体修改范围，应核对当前作者与运行状态后实施；仅提出建议不能报告为已治理。
